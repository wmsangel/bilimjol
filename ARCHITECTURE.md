# izn.study — Архитектура и ключевые решения

> Живой документ. Обновляем по мере принятия решений.
> Дата старта: 2026-08-04.

## 1. Продукт (кратко)

Образовательная платформа для детей на рынках СНГ (старт: Кыргызстан + РФ).
Аналог LogicLike, но шире по охвату:

- **Возраст:** от подготовки к школе (садик) до 11 класса.
- **Направления:** несколько предметов/навыков (не только логика).
- **Задания** делятся по классам и по уровням сложности.
- **Геймификация** (особенно для младших): личный кабинет, аватары,
  виртуальные помощники-персонажи.
- **Модель:** freemium — бесплатно ограниченное число заданий; платно —
  очень дешёвая месячная подписка.
- **Цель:** поддержание и развитие знаний, новые темы, объяснения к заданиям.

## 2. Главный архитектурный принцип: API-first

В будущем планируются **нативные приложения (Android + iOS)**. Поэтому:

- Логика, данные и бизнес-правила живут в **отдельном backend API**,
  а не внутри веб-приложения.
- Веб и мобилки — это **клиенты** одного и того же API.
- Общие типы и валидация выносятся в общий пакет и переиспользуются
  всеми клиентами.

Это исключает вариант «монолит на Next.js», из которого потом нельзя
переиспользовать backend для мобилок.

## 3. Стек (решение)

| Слой              | Технология                          | Почему |
|-------------------|-------------------------------------|--------|
| Монорепо          | pnpm workspaces + Turborepo         | Общий код между веб/мобилкой/API, единый CI |
| Backend (API)     | *(уточняется — см. §6)*             | Самохостируемый, TypeScript |
| База данных       | PostgreSQL                          | Реляционная модель заданий/прогресса/подписок |
| Веб               | Next.js (React 19)                  | Знакомый стек, SSR, SEO для лендинга |
| Мобилка (позже)   | React Native (Expo)                 | Тот же TS/React → общий код с вебом |
| Общий код         | `packages/shared` (TypeScript)      | Типы заданий, валидация (zod), API-клиент |

**Язык везде — TypeScript.** Это осознанно: одна команда, один язык,
максимум переиспользования между вебом и мобилкой.

## 4. Двуязычность (i18n)

- Языки с самого начала: **русский (ru)** и **кыргызский (ky)**.
- Архитектура i18n закладывается сразу, тексты не хардкодятся.
- Возможное расширение на другие страны СНГ — учитываем, но не усложняем сейчас.

## 5. Юридическое ограничение: 152-ФЗ (локализация ПДн в РФ)

⚠️ Для рынка РФ действует закон о локализации персональных данных:
персональные данные граждан РФ должны храниться на серверах в РФ.

**Следствия для архитектуры:**

- Backend делаем **самостоятельным и самохостируемым** — не завязываемся
  на зарубежный BaaS (Firebase/Supabase Cloud/Auth0 и т.п.) для хранения ПДн.
- Закладываем возможность развернуть БД/сервис в дата-центре РФ (и/или КР).
- Платёжные провайдеры — локальные (см. §7).

## 6. Архитектура backend (решения приняты 2026-08-04)

**Технические решения:**

| Слой | Решение | Альтернатива |
|------|---------|--------------|
| Фреймворк | **NestJS** (на Fastify-адаптере) | Hono/Fastify |
| ORM | **Prisma** + PostgreSQL | Drizzle |
| Стиль API | **REST + OpenAPI**, DTO на **zod** в `packages/shared` | tRPC |
| Auth | **email + пароль**, JWT access + refresh (телефон/соцвход — фаза 2) | Auth0/Clerk (нельзя: ПДн за рубежом) |
| Хостинг | **Self-host в РФ-ДЦ** (Yandex Cloud / Selectel / VK Cloud) | КР-ДЦ / двухрегионально |

Контент (темы/задания) **пока в коде** (`packages/shared`, версионируется в git),
API его отдаёт. Вынос в БД/CMS — отдельная фаза.

**Модель аккаунтов:** аккаунт на **родителе**, внутри — **профили детей**.
Подписка на родителе открывает премиум всем его детям. Детских ПДн — минимум
(имя, класс, аватар).

```
User (родитель)   id, email, passwordHash, locale, country, createdAt   ← ПДн (РФ)
ChildProfile      id, userId, name, avatarHelperId, grade               ← минимум ПДн
Progress          childId, taskId, correct, answeredAt                  (лучший результат)
ChildStats        childId, streak, lastActive, xp, unlockedHelpers[]
Subscription      id, userId, plan, status, provider, currentPeriodEnd
Transaction       id, userId, provider, amount, currency, status, extId
RefreshToken      id, userId, tokenHash, expiresAt, device
```

**Синхронизация (офлайн-first):** без входа всё работает на localStorage; при
входе local → server сливается; результат по задаче монотонен (правильно
остаётся правильным, OR/max), streak/XP считаются на сервере.

**Фазы реализации:**
1. Каркас API (NestJS + Postgres + Prisma), auth родителя, профили детей.
2. Синхронизация прогресса/статистики + перенос localStorage при входе.
3. Контент через API + серверный премиум-гейтинг (entitlements).
4. Платежи (КР первыми — см. §7), webhooks.
5. Харденинг: rate-limit, безопасность, экспорт/удаление (152-ФЗ), деплой в РФ-ДЦ.

## 7. Монетизация и платежи

- Подписка — очень дешёвая, ежемесячная. Активная подписка родителя = entitlement
  «премиум» для всех его детей.
- **Порядок подключения провайдеров: КР первыми** (домашний рынок):
  - **КР:** FreedomPay / Paybox + кошельки (MBANK, O!Деньги, Balance.kg, Элсом).
  - **РФ:** ЮKassa / CloudPayments (следующими).
  - Магазины приложений (позже): Apple/Google — комиссия ~15–30%.
- Карточные данные не трогаем (PCI) — только hosted-виджеты провайдера.
- Webhooks идемпотентные, с проверкой подписи; все транзакции логируются.
- Юнит-экономику считаем отдельно: стоимость привлечения vs. LTV.

## 7a. Юридическое (не код, но заложить)

- Уведомление РКН как оператора ПДн; политика конфиденциальности.
- Родительское согласие на обработку детских данных.
- Право на экспорт и удаление данных (реализуется в фазе 5).

## 8. Подход к разработке: MVP, а не «всё сразу»

Продукт задуман большим, но строим итерациями:

1. **MVP-срез:** один возраст/класс + 1–2 направления. Проверяем гипотезу
   (что дети/родители пользуются и платят).
2. Расширяем классы и предметы.
3. Геймификация (аватары, помощники).
4. Мобильные приложения.
